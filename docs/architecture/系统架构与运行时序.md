# YouLong AUV Control System：系统架构、数据流与运行时序

## 1. 文档目的与结论先行

本文以当前目录下的源码为准，解释 `AUV_zit6_cmake` 固件的启动方式、分层结构、任务（线程）、时间基准、传感器与控制数据流，以及正常工作时序。

需要先区分几个容易混淆的概念：

- “线程”在本项目中主要指 FreeRTOS/CMSIS-RTOS 的 Task。
- “定时器”可能指 STM32 的硬件 TIM、Cortex-M 的 SysTick、FreeRTOS 软件 Timer，或者仅仅是一个周期任务。
- `config.json` 是编译期配置输入，不是 MCU 运行时直接解析的文件。

在默认的 `NORMAL + AUV_HARDWARE_PRESET=1`（自研计算板/共享 UART4）组合下，稳定运行时的任务数量是：

| 类别 | 数量 | 说明 |
|---|---:|---|
| 应用任务 | 3 | `MicroRosTask`、`ControlTask`、`MonitorTask` |
| FreeRTOS 内核任务 | 2 | Idle task、Timer Service task |
| 启动过渡任务 | 1（仅启动阶段） | `app_bootstrap` 创建应用任务后自删除 |
| 稳定运行总数 | **5** | 启动阶段短暂为 6 |

默认模式下没有创建任何 FreeRTOS 软件定时器对象，因此没有用户定时器回调；但是存在两套 1 ms 时间基准：

- STM32 `TIM6`：给 HAL 提供 `HAL_GetTick()`。
- Cortex-M `SysTick`：给 FreeRTOS 调度器提供 Tick。

所以若把“时间源”都算作定时器，默认是 2 个；若只数 MCU 的 TIM 外设，则是 1 个（TIM6）。启用 I2C 深度传感器预设时，还会增加一个 `depth_i2c_poll` 任务，但它不是硬件定时器。

## 2. 源码组织与总体架构

### 2.1 构建入口

根目录的 [CMakeLists.txt](../../CMakeLists.txt) 只负责进入 `UserApp`。真正的固件目标和编译选项在 [UserApp/CMakeLists.txt](../../UserApp/CMakeLists.txt) 中定义。

主要编译参数有两个：

| 参数 | 默认值 | 作用 |
|---|---|---|
| `AUV_APP_MODE` | `NORMAL` | 选择正常运行、INS 调试、推杆调试、运动调试等应用入口 |
| `AUV_HARDWARE_PRESET` | `1` | 选择深度计、推杆和底层串口/I2C/GPIO 组合 |

构建过程会执行 `scripts/gen_config.py`，读取 [UserApp/Config/config.json](../../UserApp/Config/config.json)，生成 `UserApp/Config/SystemConfig.hpp` 和 `SystemConfig.cpp`，再把生成的 C++ 文件编译进固件。

因此配置链路是：

```text
UserApp/Config/config.json
          │  CMake 构建时
          ▼
scripts/gen_config.py
          │
          ▼
SystemConfig.hpp / SystemConfig.cpp
          │  编译、链接
          ▼
MCU 固件中的 sys_config（C++ 静态配置对象）
```

根目录的 [config.json](../../config.json) 现在是指向 `UserApp/Config/config.json` 的软链接，主要用于统一入口；CMake 实际使用的仍然是 `UserApp/Config/config.json`。程序运行时不会打开并解析磁盘上的 JSON 文件。通过 ROS 2 参数服务修改的参数也只修改 RAM 中的 `sys_config`，不会回写 JSON。

### 2.2 分层结构

```text
┌────────────────────────────────────────────────────────────────┐
│ Application                                                   │
│  AppMain / ControlTask / MicroRosTask / MonitorTask           │
│  Micro-ROS subscriptions, services, publishers                │
└───────────────┬───────────────────────┬────────────────────────┘
                │                       │
┌───────────────▼──────────────┐  ┌─────▼────────────────────────┐
│ Algorithm / Common            │  │ Components                    │
│ CascadeController             │  │ ChassisManager                │
│ PID / planner / transforms    │  │ SafetyMonitor / SoftWatchdog  │
│ MotionContext / SetpointRouter│  │ Depth / INS / USBL / pushrod  │
└───────────────┬──────────────┘  └─────┬──────────────────────────┘
                │                       │
┌───────────────▼───────────────────────▼────────────────────────┐
│ Porting / HAL                                                   │
│ UART DMA、I2C、GPIO、TIM6、IWDG、RTOS、板级串口协议            │
└────────────────────────────────────────────────────────────────┘
```

各层职责可以概括为：

1. `HAL/Core` 完成时钟、GPIO、DMA、UART、I2C、看门狗、TIM6 和 FreeRTOS 的启动。
2. `Porting` 把具体 STM32 外设包装成可被驱动调用的接口，例如环形 DMA 串口接收、I2C 读写、推力发送。
3. `Peripherals` 和 `Components` 负责 INS、USBL、深度计、推杆、电机、底盘、日志、安全监控等对象的组装和协议解析。
4. `Algorithm` 负责位置/速度/执行器三种控制级别下的控制计算。
5. `Application` 把这些能力组织成 FreeRTOS 任务，并负责 Micro-ROS 与外部 AGX/ROS 2 节点通信。

硬件对象的最终组合在 [Peripheral_Preset.cpp](../../UserApp/Porting/Presets/src/Peripheral_Preset.cpp) 中由 `AUV_HARDWARE_PRESET` 决定。这样，应用层调用的是统一的 `DepthSensor`、`Pushrod`、`INS`、`USBL` 和电机接口，底层可以换成 UART、I2C 或 GPIO 实现。

## 3. 从复位到稳定运行：启动时序

启动入口在 [main.c](../../UserApp/Peripherals/HAL/Core/Src/main.c)，CMSIS-RTOS 任务初始化在 [freertos.c](../../UserApp/Peripherals/HAL/Core/Src/freertos.c)，应用任务创建在 [AppMain.cpp](../../UserApp/Application/AppMain.cpp)。完整过程如下：

```text
MCU Reset
   │
   ▼
MPU_Config()
   │
   ▼
HAL_Init()
   │  └─ 配置 HAL Tick：TIM6，每 1 ms 进入一次中断
   ▼
SystemClock_Config()
   │
   ▼
使能 D2 SRAM，并初始化 GPIO / DMA / UART / I2C / IWDG
   │
   ├─ UART4：自研计算板/自研深度板（由预设决定）
   ├─ USART1：INS
   ├─ USART2：Micro-ROS/AGX 通信
   ├─ USART3：USBL
   ├─ USART6：电机/运动控制板
   └─ I2C1/I2C2：按硬件预设使用
   ▼
UserApp_MPU_Config()
   │  └─ D2 SRAM、AXI SRAM 配置为 DMA 友好的非 Cache 区域
   ▼
osKernelInitialize()
   │
   ▼
MX_FREERTOS_Init()
   │  └─ 创建 app_bootstrap（Realtime，约 2 KiB 栈）
   ▼
osKernelStart()
   │  └─ FreeRTOS 创建 Idle task 和 Timer Service task
   ▼
Entry_AppBootstrap()
   │
   ▼
UserApp_Start()
   │  ├─ NORMAL：创建 MicroRosTask、ControlTask、MonitorTask
   │  └─ DEBUG：只创建当前选择的调试任务
   ▼
app_bootstrap 调用 osThreadExit() 自删除
   │
   ▼
进入稳定周期运行
```

`UserApp_MPU_Config()` 把 D2 SRAM（约 `0x30000000`）和 AXI SRAM（约 `0x24000000`）设置为非 Cache 区域，主要用于避免 UART DMA 等外设与 CPU Cache 不一致。DMA 缓冲区通常位于这些区域中。

启动完成后，应用不会再回到 `main()` 的普通循环；`main()` 已经停在 `osKernelStart()` 之后的 RTOS 世界中。所有业务逻辑由任务、DMA 接收回调和外设中断驱动。

## 4. 任务/线程清单

### 4.1 NORMAL 模式

| 任务 | 创建位置 | 优先级关系 | 栈配置 | 周期/行为 | 主要职责 |
|---|---|---|---:|---|---|
| `app_bootstrap` | `freertos.c` | Realtime，最高 | `512*4` 字节 | 只运行一次 | 创建应用任务，然后退出 |
| `micro_ros_task` | `AppMain.cpp` | AboveNormal7 | `5000*4` 字节 | 2 ms | Agent 连接、Executor、订阅回调、参数服务、发布 |
| `controll_task` | `AppMain.cpp` | High | `2048*4` 字节 | 10 ms，100 Hz | 读取导航/深度/USBL，控制计算，发送推力 |
| `monitor_task` | `AppMain.cpp` | Normal | `512*4` 字节 | 100 ms，10 Hz | 安全监测、软件看门狗、刷新 IWDG |
| Idle task | FreeRTOS 内核 | Idle | 内核配置 | 无业务周期 | 空闲回收和 RTOS 基础工作 |
| Timer Service task | FreeRTOS 内核 | `configTIMER_TASK_PRIORITY=2` | `configTIMER_TASK_STACK_DEPTH=512` | 等待软件 Timer 命令 | FreeRTOS 定时器服务基础设施 |

这里的优先级只用于说明相对顺序：`ControlTask`（`High`）高于 Micro-ROS 任务（`AboveNormal7`），Micro-ROS 任务高于监控任务（`Normal`）；`app_bootstrap` 仅在启动期间具有最高优先级。实际调度仍受中断、阻塞状态和 FreeRTOS 抢占规则影响。

### 4.2 I2C 深度计预设的额外任务

当 `AUV_HARDWARE_PRESET` 使用 I2C 深度计时，[MS5837_Porting.cpp](../../UserApp/Porting/DepthSensor/src/MS5837_Porting.cpp) 会创建：

| 任务 | 栈配置 | 优先级 | 行为 |
|---|---:|---|---|
| `depth_i2c_poll` | `1024` | Normal | `vTaskDelayUntil()` 每 8 ms 运行一次，读 I2C 深度计 |

此时 NORMAL 模式稳定任务数为 6（4 个应用任务 + Idle + Timer Service），启动过渡期间短暂为 7。

该预设下，I2C 深度任务会主动调用一次 `read()`，而 `ControlTask` 的通用深度接口也会在自己的 10 ms 周期中调用 `Read()`。这是当前实现中的两条读取路径，具体驱动是否产生重复总线访问取决于 `I2C_DepthBackend` 的内部状态处理；阅读和修改 I2C 深度路径时需要特别注意这一点。

### 4.3 调试模式

`AUV_APP_MODE` 为 `MS5837_CAL_DEBUG`、`USBL_DEBUG`、`INS_DEBUG`、`PUSHROD_DEBUG` 或 `MOTION_DEBUG` 时，`UserApp_Start()` 不创建完整的三任务业务组合，而只创建对应的调试任务；随后 `app_bootstrap` 退出。

因此调试模式一般是：

```text
稳定任务数 = 1 个调试任务 + Idle + Timer Service
           = 3 个（非 I2C 深度预设）
```

若当前硬件预设还会创建 `depth_i2c_poll`，则再增加 1 个。`UserApp/Debug` 中存在一些历史调试实现，但是否计入运行任务数要以 `UserApp/Debug/CMakeLists.txt` 对当前 `AUV_APP_MODE` 实际编译的文件为准。

### 4.4 线程模型的重要特点

- 没有单独的 Micro-ROS Executor 线程。Executor 的 `rclc_executor_spin_some()` 在 `MicroRosTask` 内执行，所有订阅回调和服务回调也在该任务上下文中执行。
- 没有单独的 INS 线程或 USBL 线程。INS、USBL 和大多数 UART 深度板数据由 DMA/中断接收，在 `ControlTask` 中轮询解析。
- 没有单独的电机发送线程。控制任务直接调用电机驱动的 DMA 发送接口。
- DMA 回调只做轻量的事件通知或接收状态分发，完整协议解析通常放在任务上下文中，降低中断占用时间。

## 5. 定时器、时间基准与周期调度

### 5.1 定时器数量的准确口径

| 口径 | 数量 | 对象 | 用途 |
|---|---:|---|---|
| STM32 硬件 TIM 外设 | **1** | TIM6 | HAL 1 ms Tick、`HAL_GetTick()` |
| Cortex-M 系统 Tick | **1** | SysTick | FreeRTOS 1 ms 调度 Tick |
| FreeRTOS 软件 Timer 对象 | **0** | 无 `osTimerNew/xTimerCreate` 调用 | 没有用户 Timer 回调 |
| FreeRTOS Timer Service task | **1** | 内核任务 | 因配置启用而存在，但当前无用户 Timer 对象 |
| 独立看门狗 | **1** | IWDG1 | 故障复位保护，不负责业务周期调度 |

TIM6 和 SysTick 都是 1 ms，但它们不是同一个机制：TIM6 服务 STM32 HAL 时间，SysTick 驱动 FreeRTOS 任务切换。两者的回调、中断链路和用途都不同。

### 5.2 TIM6：HAL 时间基准

在 [stm32h7xx_hal_timebase_tim.c](../../UserApp/Peripherals/HAL/Core/Src/stm32h7xx_hal_timebase_tim.c) 中，TIM6 被配置为约 1 MHz 的计数频率，自动重装周期对应 1 ms。TIM6 更新中断经过：

```text
TIM6_DAC_IRQHandler
       ▼
HAL_TIM_IRQHandler(&htim6)
       ▼
HAL_TIM_PeriodElapsedCallback()
       ▼
HAL_IncTick()
       ▼
HAL_GetTick() 返回毫秒计数
```

应用中的超时判断，例如 Agent 重连、发布频率、深度诊断和推杆 ACK 重试，主要使用这个毫秒计数。

### 5.3 SysTick：FreeRTOS 调度基准

`FreeRTOSConfig.h` 将 `configTICK_RATE_HZ` 设置为 1000，因此 FreeRTOS Tick 也是 1 ms。SysTick 中断进入 FreeRTOS 的 `xPortSysTickHandler()`，递增任务 Tick，并在需要时触发 PendSV 完成上下文切换。

控制任务采用：

```cpp
vTaskDelayUntil(&wake_tick, pdMS_TO_TICKS(10));
```

Micro-ROS 任务和监控任务也使用 `vTaskDelayUntil()`，所以它们的周期调度以 FreeRTOS Tick 为准，并不是通过创建硬件定时器实现的。

### 5.4 应用周期表

| 逻辑 | 代码位置 | 标称周期 | 时间基准 | 备注 |
|---|---|---:|---|---|
| Micro-ROS 主循环 | `MicroRosTask.cpp` | 2 ms | FreeRTOS Tick | 约 500 Hz；连接失败时会进入更长等待 |
| 控制循环 | `ControlTask.cpp` | 10 ms | FreeRTOS Tick | 100 Hz；控制器固定使用 `dt=0.01 s` |
| 监控循环 | `MonitorTask.cpp` | 100 ms | FreeRTOS Tick | 10 Hz |
| I2C 深度轮询 | `I2C_DepthBackend` | 8 ms | FreeRTOS Tick | 仅 I2C 深度预设，约 125 Hz 轮询 |
| Agent 在线探测 | `MicroRosTask.cpp` | 连接后 2000 ms | `HAL_GetTick()` | 失败则断开并重新连接 |
| ROS 心跳发布 | `MicroRosPublisher.cpp` | 1000 ms | `HAL_GetTick()` | 1 Hz |
| 状态发布 | `MicroRosPublisher.cpp` | 100 ms | `HAL_GetTick()` | 10 Hz |
| 位置/推力发布 | `MicroRosPublisher.cpp` | 约 33 ms | `HAL_GetTick()` | 标称约 30 Hz |
| 速度发布 | `MicroRosPublisher.cpp` | 20 ms | `HAL_GetTick()` | 标称 50 Hz |
| 深度诊断 | `ControlTask.cpp` | 1000 ms | `HAL_GetTick()` | 只打印诊断，不创建 Timer |
| 推杆 ACK 重试 | `MicroRosSubscriber.cpp` | 100 ms | `HAL_GetTick()` | 只在存在待确认命令时发生 |

表中后半部分是“在任务循环里用时间差判断”的周期门控，不是 RTOS Timer 对象。

## 6. NORMAL 模式的数据流

### 6.1 外部命令到执行器

```text
ROS 2 / AGX
    │
    │  Micro-ROS XRCE-DDS 数据
    ▼
USART2 + 自定义 transport
    │
    │  中断/DMA 接收，MicroRosTask 中 spin_some()
    ▼
rclc Executor
    │
    ├─ /zit6/cmd/setpoint ──► SetpointRouter / ChassisManager
    ├─ /zit6/cmd/agxhbt ────► SafetyMonitor 心跳状态
    ├─ /zit6/cmd/ins ───────► INS 驱动开关/复位命令
    ├─ /zit6/cmd/servo ─────► 电机/舵机驱动
    ├─ /zit6/cmd/light ─────► 灯光输出
    ├─ /zit6/cmd/pushrod ───► 推杆命令队列
    └─ /zit6/sim/nav ───────► sitl_nav_queue
    │
    ▼
ControlTask 每 10 ms 读取共享状态
    │
    ▼
底盘控制器：位置/速度/执行器级联控制
    │
    ▼
MotionController_Porting
    │  USART6 TX DMA
    ▼
电机控制板 / 推进器
```

`/zit6/cmd/setpoint` 回调会先检查数值是否有限、是否已经 armed、模式是否有效；位置和速度模式还要求导航状态有效（仿真路径除外）。通过检查后，回调将目标写入 `MotionContext`，控制器在下一个控制周期使用它。

### 6.2 真实传感器到控制器

```text
INS ─ USART1 RX DMA ─► INS_Porting ─► INS_Driver::update()
                                             │
USBL ─ USART3 RX DMA ─► USBL_Porting ─► USBL_Driver::update()
                                             │
深度板 ─ UART4 RX DMA ─► Self_CalcBoard_Porting ─► 深度/推杆共享协议
                                             │
I2C 深度计 ─ I2C1 ─► I2C_DepthBackend（仅 I2C 预设）
                                             │
                                             ▼
                                      ControlTask
                                             │
                       NavState + 深度 Z + USBL 最新数据
                                             │
                                             ▼
                                      ChassisManager
```

各输入的处理方式不同：

- INS 和 USBL 使用环形 DMA 缓冲区，接收中断/回调负责保存接收事件，任务负责解析完整帧。
- 默认自研计算板预设中，UART4 的 RX DMA 由 `Self_CalcBoard_Porting` 统一拥有；深度和推杆共享一条字节流，避免多个对象同时操作同一 UART DMA。
- UART 深度后端通常由 `ControlTask` 通过 `depth_sensor->Read()` 推进解析；I2C 深度预设另外有 `depth_i2c_poll` 任务。
- USBL 数据不会直接融合进 INS 导航状态。控制任务把有效 USBL 样本放入 `usbl_topic_queue`，随后由 Micro-ROS 发布为 `/zit6/state/USBL`。

### 6.3 控制反馈到 ROS 2

控制任务将导航、目标、推力、执行时间、超时和发送失败计数写入共享 `MotionContext`。Micro-ROS 任务每次循环调用发布器，发布器根据 `HAL_GetTick()` 的时间门控拆成不同频率：

```text
MotionContext / 队列
        │
        ▼
MicroRosPublisher::publish()
        │
        ├─ /zit6/state/pos       位置
        ├─ /zit6/state/vel       速度
        ├─ /zit6/state/thr       推力输出
        ├─ /zit6/state/zithbt    设备心跳
        ├─ /zit6/state/status    综合状态
        ├─ /zit6/state/USBL      USBL FIFO
        └─ /zit6/log             日志队列中每次取一条
        │
        ▼
USART2 + Micro-ROS transport
        │
        ▼
ROS 2 / AGX
```

发布器本身没有线程；它只是被 `MicroRosTask` 周期调用。日志也没有独立发送任务：`RosLogger` 把日志非阻塞地放入长度为 10 的 FreeRTOS 队列，再由 Micro-ROS 发布器逐次取出。

### 6.4 推杆数据流

```text
/zit6/cmd/pushrod
        │
        ▼
Micro-ROS 回调校验：speed、duration、armed、队列容量
        │
        ▼
本地 pushrod_queue（容量 4）
        │
        ▼
MicroRosTask::updatePushrod()
        │
        ├─ 启动排队命令
        ├─ 100 ms ACK 超时/重试
        ├─ 读取 ACK
        └─ 失去 armed 时停止或清空
        │
        ▼
UART4 共享后端或 GPIO 后端
        │
        ▼
推杆机构
```

对于默认共享 UART4 的后端，UART 接收轮询由深度/计算板共享链路统一完成；推杆后端的 `poll()` 本身不再重复读取同一串口。

## 7. NORMAL 模式单周期工作时序

### 7.1 启动后的首次业务循环

```text
app_bootstrap
  ├─ 创建 micro_ros_task
  ├─ 创建 controll_task
  ├─ 创建 monitor_task
  └─ 退出

ControlTask 首次运行
  ├─ 清空 INS 接收缓存
  ├─ 初始化 INS、USBL、底盘、日志
  ├─ 创建 SITL 导航队列（长度 3）
  ├─ 创建 USBL 队列（长度 8）
  ├─ 初始化并启动深度驱动
  ├─ 如有 GPIO 推杆，初始化并启动推杆
  └─ 设置第一次唤醒时间

MicroRosTask 首次运行
  ├─ 配置 cJSON allocator
  ├─ 尝试 ping Agent
  └─ 成功后创建 node、subscriber、service、publisher、executor

MonitorTask 首次运行
  ├─ 初始化 SoftWatchdog
  └─ 设置第一次监控唤醒时间
```

任务首次运行顺序不应理解为固定的源码顺序。FreeRTOS 会依据优先级和阻塞状态调度：在常驻应用任务中，ControlTask 优先级最高，Micro-ROS 其次，MonitorTask 最低；任务初始化函数内部若发生阻塞，调度器可能切换到其他就绪任务。

### 7.2 一个约 10 ms 的控制周期

控制任务 [ControlTask.cpp](../../UserApp/Application/ControlTask.cpp) 的核心顺序如下：

```text
进入周期
  │
  ├─ 读取 FreeRTOS Tick，计算实际 dt
  ├─ 记录 HAL_GetTick() 作为执行时间起点
  ├─ updateNavigation()
  │    ├─ HITL：使用内部仿真状态（如启用）
  │    ├─ SITL：从 sitl_nav_queue 取最新一帧
  │    └─ 真实模式：INS + USBL + 深度传感器
  ├─ 应用 home offset：位置平移、姿态旋转和角度归一化
  ├─ MotionContext::nav_state_ 写入最新导航状态
  ├─ ChassisManager 更新控制器
  │    ├─ ControlLevel::NONE       ─► 零输出
  │    ├─ POSITION                  ─► 位置 PID → 速度 PID
  │    ├─ VELOCITY                  ─► 速度 PID
  │    └─ ACTUATOR                  ─► 直接推力
  ├─ 保存 last_output_forces
  ├─ armed 时按电机顺序发送推力；否则发送 6 路零推力
  ├─ 记录执行耗时、发送失败和 overrun
  └─ vTaskDelayUntil(..., 10 ms)
```

控制器的 `dt` 固定为 `0.01f`，而任务同时测量实际周期。如果一次控制计算耗时超过 10 ms，代码会增加 overrun 计数并记录日志。也就是说，实际调度有监控，但 PID 计算仍按设计周期 10 ms 工作。

### 7.3 一个约 2 ms 的 Micro-ROS 周期

`MicroRosTask` 的正常连接路径为：

```text
循环开始
  │
  ├─ 喂 Micro-ROS 软件看门狗
  ├─ WAITING_AGENT：ping Agent（失败则等待约 100 ms）
  │
  └─ CONNECTED：
       ├─ 每 2 s ping 一次 Agent
       ├─ ping 失败：销毁 ROS 实体并回到 WAITING_AGENT
       ├─ executor.spin_some(..., 1 ms)
       ├─ 执行订阅回调和服务回调
       ├─ 更新推杆状态、ACK 和重试
       ├─ subscriber_.update()
       ├─ publisher_.publish()
       └─ vTaskDelayUntil(..., 2 ms)
```

Agent 不在线时不会创建或持续使用完整 ROS 实体；连接成功后才初始化 node、executor、订阅器、服务和发布器。断开时会按相反方向清理这些对象，然后继续等待重连。

### 7.4 一个约 100 ms 的监控周期

```text
MonitorTask
  ├─ 检查 SoftWatchdog 是否允许刷新硬件 IWDG1
  ├─ SafetyMonitor::check(HAL_GetTick())
  │    ├─ 检查 armed 状态下 AGX 心跳是否超时
  │    ├─ 检查导航条件和控制级别
  │    └─ 必要时强制 disarm，并清零控制级别
  ├─ 通过 HAL_IWDG_Refresh() 刷新 IWDG1
  └─ 延时 100 ms
```

软件看门狗维护 Micro-ROS、INS、DEPTH 等逻辑源的最后喂狗时间。当前配置是否检查 INS/DEPTH 由 `config.json` 的 `system.soft_watchdog` 字段决定；硬件 IWDG 是最终的 MCU 复位保护，不是用来产生 100 ms 任务周期的定时器。

## 8. 命令、状态和共享数据的并发关系

### 8.1 `MotionContext` 是控制状态汇聚点

`MotionContext` 保存：

- 当前 `NavState`：位置使用世界/NED 坐标，速度使用机体/FRD 坐标。
- 当前目标：世界位置、机体速度或机体推力。
- 控制级别：`NONE`、`POSITION`、`VELOCITY`、`ACTUATOR`。
- 最近一次推力输出、控制周期、执行时间、overrun 和 TX fail 计数。
- armed 状态相关的 home offset。
- SITL 导航队列和 USBL 发布队列。

共享字段使用 `LockedField` 和临界区保护，Micro-ROS 回调可以写入目标，ControlTask 可以读取并计算。需要注意，所有数据并非都通过同一种锁保护；队列使用 FreeRTOS Queue，部分组件状态使用组件自己的同步方式，阅读新增字段时不能默认它们全部是原子或线程安全的。

### 8.2 队列容量与溢出策略

| 队列 | 容量 | 生产者 | 消费者 | 满时策略 |
|---|---:|---|---|---|
| `sitl_nav_queue` | 3 | `/zit6/sim/nav` 回调 | `ControlTask` | 控制任务取最新状态，旧状态可能被覆盖/丢弃 |
| `usbl_topic_queue` | 8 | `ControlTask` | `MicroRosPublisher` | 满时先丢弃最旧样本，再放入新样本 |
| 推杆命令队列 | 4 | `/zit6/cmd/pushrod` 回调 | `MicroRosTask` | 满时拒绝新命令 |
| 日志队列 | 10 | `RosLogger` | `MicroRosPublisher` | 非阻塞入队，满时当前日志可能丢失 |

这种设计把高优先级、短路径的通信回调与较重的传感器解析和控制计算隔开，同时避免发布或日志阻塞控制循环。

## 9. 控制算法和安全约束

### 9.1 目标到推力

`SetpointRouter` 根据命令中的模式位选择目标类型，并负责世界坐标/机体坐标转换、增量目标和字段 mask 处理。`CascadeController` 再按照当前 `ControlLevel` 计算：

```text
POSITION：位置误差
              ▼
          位置 PID
              ▼
        期望机体速度
              ▼
          速度 PID
              ▼
            推力

VELOCITY：期望机体速度 ─► 速度 PID ─► 推力

ACTUATOR：直接机体推力 ─────────────► 限幅输出

NONE：   ─────────────────────────► 六路零输出
```

最终输出会进行限幅。控制任务还会根据 armed 状态决定是否真正发送目标推力；未 armed 时无条件发送六路零值。

### 9.2 armed、心跳和 home offset

- AGX 心跳回调记录最后接收时间、数据类型和计数。
- 进入 armed 前需要满足心跳数量、持续时间以及对应导航条件。
- armed 后如果心跳超过约 1000 ms 未更新，`SafetyMonitor` 会强制 disarm。
- 执行 arm 时记录当前位置和 yaw 作为 home offset，roll/pitch 归零；disarm 时清除 home offset 和控制级别。
- 位置/速度命令在未 armed、导航无效或数值非法时会被拒绝或不进入有效控制目标。

## 10. 不同硬件预设对架构的影响

硬件预设定义在 [Hardware_Preset.h](../../UserApp/Porting/Presets/inc/Hardware_Preset.h)。它改变的是底层设备组合和少数任务数量，不改变上层三任务的基本控制模型。

| 预设 | 深度后端 | 推杆后端 | 额外任务 |
|---:|---|---|---|
| 1 | 自研 UART/计算板 | 共享 UART | 无 |
| 2 | 自研 UART/计算板 | GPIO | 无 |
| 3 | 商用深度板 | 自研 UART | 无 |
| 4 | M14 深度板 | 自研 UART | 无 |
| 5 | I2C 深度计 | 自研 UART | `depth_i2c_poll` |
| 6 | 商用深度板 | GPIO | 无 |
| 7 | M14 深度板 | GPIO | 无 |

几个关键差异：

- 非 I2C 深度板通常使用 UART RX DMA，解析在控制任务或相应驱动轮询中完成，因此不增加独立深度任务。
- GPIO 推杆使用 GPIO 后端，命令持续时间到期后由推杆后端停止输出。
- 默认预设 1 中，深度和推杆共享 UART4 字节流；`Self_CalcBoard_Porting` 是这条 RX DMA 的唯一拥有者。
- 预设 5 的 I2C 深度轮询会增加一个 RTOS 任务，并且要关注它与 `ControlTask` 通用 `Read()` 路径的交互。

## 11. 配置与运行时修改

### 11.1 编译期配置

`config.json` 中的内容被生成器转换成 C++ 常量/对象，典型配置包括：

- 系统看门狗超时和启用项。
- 深度数据来源选择。
- 底盘质量、阻力、推力系数和静态浮力参数。
- 位置/速度 PID 以及各控制 profile 的限幅。
- INS 初始纬度、经度和高度。
- HITL/SITL 仿真开关。

硬件后端本身主要由 `AUV_HARDWARE_PRESET` 编译宏选择；JSON 中的 `depth_calc_board.enabled` 不会替代这个编译期硬件组合选择。

### 11.2 运行时参数服务

Micro-ROS 提供：

- `/zit6/update_params`
- `/zit6/get_params`

服务层使用预分配的 JSON 缓冲区和参数路径/值序列，避免频繁动态分配。更新成功后会修改内存中的 `sys_config`，并重新应用底盘等组件的相关配置；获取参数返回的也是当前内存状态。

当前实现没有把更新后的参数写回 `UserApp/Config/config.json`，设备重启或重新烧录后仍会回到编译进固件的配置。

## 12. 关键时序关系与可能的误读

### 12.1 任务周期不等于数据到达周期

UART DMA 接收和外设中断可以在任意时刻到达；10 ms 控制任务只是定期消费已经到达的数据。因此：

```text
串口帧到达 ─► DMA/IRQ 立即搬运或置位事件
                  │
                  └─► 下一次对应任务运行时解析/更新状态
```

数据延迟取决于帧到达时间、任务阻塞和当前优先级，不应简单认为所有传感器都严格 100 Hz。

### 12.2 Micro-ROS 回调不会直接执行控制计算

setpoint 回调主要负责校验并更新目标；实际控制输出在下一次 `ControlTask` 周期计算。这样可以让控制输出保持固定调度，但命令到推力之间至少存在一个任务调度间隔。

### 12.3 发布频率与控制频率不同

控制输出计算是 100 Hz；位置、推力和速度等 ROS 状态发布分别是约 30 Hz、50 Hz 等。发布器不应被当作控制环的一部分，也不应从发布频率反推控制频率。

### 12.4 FreeRTOS Timer Service 存在不等于使用了软件定时器

`configUSE_TIMERS=1` 会让 FreeRTOS 创建 Timer Service task，即使应用没有创建任何 Timer 对象。当前应用的周期工作主要由任务 `vTaskDelayUntil()` 和 `HAL_GetTick()` 时间差完成。

### 12.5 仿真路径替换的是导航输入，不是整个应用

- HITL 路径使用内部仿真状态并根据控制力推进仿真。
- SITL 路径从 `/zit6/sim/nav` 接收导航数据。
- 两种路径仍保留 Micro-ROS、控制任务、监控任务和推力输出框架；它们只是替换真实 INS/深度输入或仿真推进部分。

## 14. 一句话总结

这个固件是一个“中断/DMA 负责及时搬运，三个主要 RTOS 任务负责通信、控制和安全，组件负责设备协议，算法负责推力计算”的分层系统：Micro-ROS 每 2 ms 处理外部命令和状态发布，ControlTask 每 10 ms 完成导航读取与控制输出，MonitorTask 每 100 ms 执行安全检查；TIM6 和 SysTick 各自提供 1 ms 时间基准，而当前没有真正的 FreeRTOS 软件定时器对象。
