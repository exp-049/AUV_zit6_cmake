# MS5837 深度传感器数据协议

版本：V1.0（串口）  
角色：主设备（Host）为主站，MS5837 核心单片机（Device）为从站。

## 1. 协议目标

核心单片机上电完成传感器初始化后，默认以 **60 Hz** 向主设备发送深度和温度数据。主设备可以通过串口修改回传频率，也可以随时主动发送握手帧确认设备是否在线及当前配置。

本协议的回传频率指“数据帧发送频率”。频率配置范围为 **15～150 Hz，包含边界，单位为整数 Hz**。

## 2. 串口参数

除非整机另有约定，串口使用以下参数：

| 参数 | 值 |
|---|---|
| 波特率 | 115200 bit/s |
| 数据位 | 8 |
| 校验位 | 无 |
| 停止位 | 1 |
| 流控 | 无 |
| 字节序 | 小端序（Little-endian） |

所有多字节整数均按低字节在前传输。浮点数不直接上行，统一使用定点整数。

## 3. 通用数据帧格式

串口上的所有 V1 帧均采用以下格式：

```text
┌──────┬──────┬──────┬──────┬──────────────┬──────────┐
│ SOF1 │ SOF2 │ TYPE │ LEN  │ PAYLOAD      │ CHECKSUM │
│  A5  │  5A  │ 1字节 │ 1字节 │ LEN 个字节   │ 1字节    │
└──────┴──────┴──────┴──────┴──────────────┴──────────┘
```

- `SOF1/SOF2`：固定为 `0xA5 0x5A`。
- `TYPE`：帧类型。
- `LEN`：`PAYLOAD` 的字节数，最大 32；不包含帧头、类型、长度和校验字节。
- `CHECKSUM`：`TYPE`、`LEN` 和全部 `PAYLOAD` 字节的逐字节 XOR 结果；不包含 `SOF1/SOF2`。
- 帧之间不需要 `CR`、`LF` 或其他分隔符。

接收方应先查找 `0xA5 0x5A`，再按 `LEN` 读取完整帧；长度超限或校验错误时丢弃当前帧并重新寻找帧头。

## 4. Device → Host：深度温度数据帧

数据帧 `TYPE = 0x01`，`LEN = 11`，总长度为 16 字节。

| PAYLOAD 字节 | 字段 | 类型 | 单位/含义 |
|---|---|---|---|
| 0～1 | `depth_cm` | `uint16_t` | 深度，单位 cm；实际深度 = `depth_cm / 100` m |
| 2～5 | `pressure_01mbar` | `uint32_t` | 绝对压力，单位 0.1 mbar；实际压力 = `pressure_01mbar / 10` mbar |
| 6～7 | `temp_01c` | `int16_t` | 温度，单位 0.1 °C；实际温度 = `temp_01c / 10` °C |
| 8～9 | `sample_seq` | `uint16_t` | 数据序号，每发送一帧加 1，溢出后从 0 重新计数 |
| 10 | `status` | `uint8_t` | 当前数据状态，见下表 |

`status` 定义：

| 位 | 名称 | 置 1 的含义 |
|---|---|---|
| bit0 | `SENSOR_OK` | 本次传感器采样有效 |
| bit1 | `CALIBRATED` | 已完成上电大气压校准 |
| bit2 | `DATA_NEW` | 本帧包含新采样结果；为 0 时表示发送的是最近一次有效结果 |
| bit3～7 | 保留 | 必须发送 0，接收方忽略 |

正常工作时 `SENSOR_OK` 和 `CALIBRATED` 应为 1。深度使用当前工程的淡水换算结果，非负值；若计算结果超出 `uint16_t` 可表示范围，发送端应饱和到 `0xFFFF`。

### 数据帧示例

以下示例表示：深度 12.34 m、压力 10132.5 mbar、温度 23.4 °C、序号 7，状态正常：

```text
A5 5A 01 0B D2 04 8D 7B 00 00 EA 00 07 03 C4
```

其中 `10` 为 `TYPE`、`LEN` 和 11 字节负载的 XOR 校验值。

## 5. Host → Device：设置回传频率

设置频率请求 `TYPE = 0x10`，`LEN = 3`：

| PAYLOAD 字节 | 字段 | 类型 |
|---|---|---|
| 0 | `request_id` | `uint8_t` |
| 1～2 | `requested_rate_hz` | `uint16_t` |

主设备发送完整请求后，Device 必须返回确认帧。`request_id` 由主设备生成，Device 原样回显，用于匹配请求和确认。

确认帧 `TYPE = 0x90`，`LEN = 6`：

| PAYLOAD 字节 | 字段 | 类型 | 含义 |
|---|---|---|---|
| 0 | `request_id` | `uint8_t` | 对应请求的 ID |
| 1 | `result` | `uint8_t` | 结果码，见下表 |
| 2～3 | `requested_rate_hz` | `uint16_t` | 原请求频率 |
| 4～5 | `applied_rate_hz` | `uint16_t` | 当前实际配置频率 |

`result` 定义：

| 值 | 名称 | 处理方式 |
|---|---|---|
| `0x00` | `OK` | 请求有效，应用请求频率 |
| `0x01` | `OUT_OF_RANGE` | 请求小于 15 Hz 或大于 150 Hz；保持原频率 |
| `0x02` | `INVALID` | 长度或参数格式错误；保持原频率 |
| `0x03` | `BUSY` | 当前暂时无法应用；保持原频率，可稍后重试 |

有效频率的判断为 `15 <= requested_rate_hz <= 150`。同一个频率重复设置也必须返回 `OK` 确认。确认帧应在收到请求并完成校验后尽快发送；确认发送完成后，下一帧数据开始按照 `applied_rate_hz` 调度。

频率设置只改变数据帧的发送周期，不改变数据单位和帧格式。周期近似为 `1000 / applied_rate_hz` ms。若一次 MS5837 采样尚未完成，Device 可以发送最近一次有效值，此时应将 `DATA_NEW` 清零。

## 6. Host → Device：主动握手

握手请求 `TYPE = 0x20`，`LEN = 4`：

| PAYLOAD 字节 | 字段 | 类型 |
|---|---|---|
| 0～3 | `host_nonce` | `uint32_t` |

`host_nonce` 由主设备生成，建议每次握手使用不同值。Device 收到有效握手后必须返回握手确认帧。

握手确认 `TYPE = 0xA0`，`LEN = 9`：

| PAYLOAD 字节 | 字段 | 类型 | 含义 |
|---|---|---|---|
| 0～3 | `host_nonce` | `uint32_t` | 原样回显，用于匹配握手 |
| 4 | `protocol_version` | `uint8_t` | 当前为 `0x01` |
| 5 | `device_state` | `uint8_t` | 设备状态，见下表 |
| 6～7 | `current_rate_hz` | `uint16_t` | 当前数据回传频率 |
| 8 | `sensor_flags` | `uint8_t` | 传感器状态，见下表 |

`device_state` 定义：

| 值 | 含义 |
|---|---|
| `0x00` | 初始化中 |
| `0x01` | 就绪，正常工作 |
| `0x02` | 传感器初始化或采样故障 |

`sensor_flags` 定义：

| 位 | 含义 |
|---|---|
| bit0 | MS5837 初始化成功 |
| bit1 | 大气压校准完成 |
| bit2 | 存在最近一次有效采样 |
| bit3～7 | 保留，发送 0 |

### 握手示例

主设备发送 `host_nonce = 0x12345678`：

```text
A5 5A 20 04 78 56 34 12 2C
```

Device 回复（就绪、60 Hz、传感器正常）：

```text
A5 5A A0 09 78 56 34 12 01 01 3C 00 07 9A
```

## 7. Host → Device：推杆任务帧

推杆采用单任务单帧，不使用多帧事务。FIFO 只用于缓冲已经确认接收的任务。

任务帧 `TYPE = 0x30`，`LEN = 12`：

| PAYLOAD 字节 | 字段 | 类型 | 含义 |
|---|---|---|---|
| 0～3 | `task_id` | `uint32_t` | 任务 ID，默认从 0 开始 |
| 4～5 | `power_x1000` | `int16_t` | 归一化功率乘 1000，范围 -1000～1000 |
| 6～9 | `duration_ms` | `uint32_t` | 工作时长，单位 ms，必须大于 0 |
| 10～11 | `task_crc16` | `uint16_t` | CRC-16/CCITT-FALSE，低字节在前 |

`power_x1000` 的含义：

| 值 | 含义 |
|---|---|
| `1000` | 100% 正转 |
| `500` | 50% 正转 |
| `0` | 停止 |
| `-500` | 50% 反转 |
| `-1000` | 100% 反转 |

`task_crc16` 计算范围为：`TYPE`、`LEN` 以及 Payload 的字节 0～9，算法为
CRC-16/CCITT-FALSE（初值 `0xFFFF`，多项式 `0x1021`）。外层帧的
`CHECKSUM` 仍按通用 XOR 规则计算。

### 推杆任务确认

确认帧 `TYPE = 0xB0`，`LEN = 7`：

| PAYLOAD 字节 | 字段 | 类型 |
|---|---|---|
| 0～3 | `task_id` | `uint32_t` |
| 4 | `result` | `uint8_t` |
| 5 | `queue_count` | `uint8_t`，当前等待执行的任务数 |
| 6 | `ready` | `uint8_t`，10 秒复用完成后为 1 |

`result` 定义：

| 值 | 名称 | 含义 |
|---|---|---|
| `0x00` | `OK` | 已加入 FIFO |
| `0x01` | `INVALID_FRAME` | 帧格式或参数非法 |
| `0x02` | `CRC_ERROR` | 保留；CRC 错误帧通常不回复 |
| `0x03` | `POWER_OUT_OF_RANGE` | 功率不在 -1000～1000 |
| `0x04` | `DURATION_INVALID` | 时长为 0 或超出允许范围 |
| `0x05` | `ID_OUT_OF_ORDER` | 新 ID 不大于上一个已接受 ID |
| `0x06` | `ID_CONFLICT` | 相同 ID 但任务内容不同 |
| `0x07` | `QUEUE_FULL` | FIFO 已满，任务未加入 |
| `0x08` | `NOT_INITIALIZED` | 推杆组件尚未初始化 |

### ID 与重发规则

1. 正常情况下首个任务 `task_id = 0`，之后新任务 ID 必须严格递增。
2. 帧校验失败或超时没有确认时，主机使用相同 `task_id` 原样重发。
3. 设备已加入某个任务后，再收到相同 ID 且内容完全相同的任务，只重发 `OK`，不重复加入 FIFO。
4. 相同 ID 但内容不同返回 `ID_CONFLICT`；小于最近已接受 ID 返回 `ID_OUT_OF_ORDER`。
5. 返回 `QUEUE_FULL` 时任务未被接受，主机保持当前 ID，等待队列有空间后重试。
6. 只有收到 `OK` 后，主机才递增 ID 并发送下一个任务。
7. 10 秒复用完成前，任务仍可加入 FIFO；复用完成后按 FIFO 顺序执行。

CRC、长度或外层 XOR 错误时，设备不执行任务。由于此时不能信任
`task_id`，设备可以不回复，主机按超时规则使用原 ID 重发。

## 8. 上电、异常与重试约定

1. 每次上电或复位后，回传频率恢复为 60 Hz；频率配置不写入 Flash。
2. Device 初始化成功后开始发送数据帧；初始化失败时仍应响应握手，但 `device_state = 0x02`。
3. 主设备发送设置频率请求后，若在 100 ms 内未收到对应确认，可重发；重发应使用相同 `request_id`，Device 不应因重复请求产生额外副作用。
4. 主设备必须每 **2 s** 发送一次有效握手，用于检测通信链路和传感器状态；握手不会改变当前频率。设备端只有收到并校验通过的握手帧后才刷新看门狗。
5. 设备端看门狗超时时间约为 **5 s**。若连续超过该时间没有收到有效握手，设备由 IWDG 自动复位。IWDG 使用 LSI 时，实际超时时间会随芯片和温度存在误差。
6. 接收到未知 `TYPE` 时，Device 可忽略该帧；不得影响后续数据发送，也不能刷新看门狗。
7. 校验错误、帧头错误或长度错误的帧直接丢弃，不执行其中的命令，也不能刷新看门狗。

## 9. 与当前工程实现的关系

当前工程已按本文 V1 协议启用 USART1：

- `PA9`：USART1_TX
- `PA10`：USART1_RX
- 115200 bit/s，8N1，无流控
- 默认数据发送频率为 60 Hz
- 支持 `TYPE=0x10` 设置频率和 `TYPE=0x20` 主动握手
- 自研 UART 后端在 `UserApp/Peripherals/Presets/SelfCalcBoard/src/UART_MS5837Backend.cpp` 内部完成
  深度帧解析、握手和链路状态维护
- 推杆任务编解码也由同一自研 UART 后端内部完成，以保证深度和推杆共享一套
  UART4 DMA 帧解析器
- 当前 STM32 的 USART 组件位于 `Software/Peripherals/uart_component.c/.h`，默认使用 USART1 DMA+IDLE 接收，开关为
  `UART_COMPONENT_USE_DMA_IDLE`；关闭时回退到单字节接收中断。
- 主设备每 2 s 发送一次 `HANDSHAKE`；设备端仅在有效握手后调用 IWDG 刷新，
  看门狗配置约为 5 s（`IWDG_PRESCALER_64`、`Reload=3124`）。

数据帧发送由主循环调度。MS5837 采样尚未完成时，设备发送最近一次有效值，并清除 `DATA_NEW`。

SEGGER RTT 通道 0 仅用于调试状态输出，不承载 V1 协议数据。

历史兼容格式如下，当前设备端不再通过 RTT 发送：

```text
A5 5A depth_cm(2) pressure_01mbar(4) temp_01c(2) XOR(1)
```

可移植的软件协议层不依赖 HAL 或具体 UART 外设。DMA+IDLE 的一次回调不
保证对应一个完整帧，适配层应把收到的每个字节依次交给解析器；因此半帧、
整帧和多帧连续到达均可处理。其他平台只需把
`UserApp/Peripherals/Presets/SelfCalcBoard/src/UART_MS5837Backend.cpp` 中的后端实现，并在自己的
UART 接收回调中逐字节调用 `Self_CalcBoard_Link::onRxByte()` 即可。
